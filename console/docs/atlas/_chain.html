The refusal engine.

main · 55c636a

The chain layer does not decide whether a proposal is wise. It decides whether a transaction is the transaction the vote committed to. The interesting property is refusal: an unapproved selector, a hidden multicall child, a stale version or an implementation whose code hash changed must not execute.

Executor gate

01 · recomputeactionsHash, intentHash, commitment from chain id, executor and fields.
02 · stateMust be Queued; otherwise ProposalNotInState.
03 · timelockblock.timestamp ≥ eta; otherwise TimelockNotExpired.
04 · versionRegistry latest must equal the submitted version hash; otherwise VersionSuperseded.
05 · rulesTop-level action count must equal rule count; each action is enforced exactly.
06 · effects firstState is written before interactions; a re-entrant recipient cannot execute twice.
07 · postconditionsAllowance ceiling only. Balance-drain and native-value cap are not implemented.
Honest edges
· A commitment mismatch surfaces as ProposalNotInState(Queued, Empty), not CommitmentMismatch.
· There is no native-value check; value is bound in actionsHash but no ceiling exists.
· _postConditionChecks is an allowance check; the comment about balance decrease is not code.
· castVote, Defeated, syncFromExecutor, cancelProposal and returnBond have no test in A's checked-in suite.
CodeHashMismatch uses keccak256("") as observed code hashonly call · no delegatecall path

Action kinds

ERC20_TRANSFER · 0

Exact target, selector, recipient and amount ceiling. Calldata length 68.

ERC20_APPROVE · 1

Exact spender, bounded ceiling, explicit unlimited-approval guard.

PARAM_SET · 2

Selector plus first uint256 within maxAmount; semantic matching is out of scope.

UPGRADE · 3

Implementation address and extcodehash check. Code swapped after the vote reverts.

OWNERSHIP_TRANSFER · 4

Exact new owner; hidden ownership inside a multicall fails the child rule.

MULTICALL · 5

Depth < 2, child count matches, every child consumes its own committed rule.

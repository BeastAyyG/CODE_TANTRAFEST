# Hardware-wallet signing

Aegis IntentLock signs votes and guardian halts as EIP-712 typed data. The signer
can be a pair of Ledger devices connected through the Device Management Kit
(DMK), a browser wallet, or the server-side dev signer. Voter and guardian keys
never leave the signing device; a funded relayer submits the transaction.

## Connection options

| Option | Signer tag | Key location | Use |
| :--- | :--- | :--- | :--- |
| Dev signer | `DEV SIGNER` | Hardhat unlocked account or an env key on the server | Default and failure fallback |
| Browser wallet | `BROWSER WALLET` | MetaMask / EIP-1193 wallet | Non-hardware signing and guardian test wallet |
| Ledger | `HARDWARE` | Ledger device through WebHID | Hardware vote and guardian halt |

The top bar and every receipt display the tag. `HARDWARE` is only shown after the
direct Ledger DMK connector returns the signature. A browser wallet backed by a
Ledger is still labelled `BROWSER WALLET`, because the app cannot verify the
wallet's internal signer.

### Ledger packages

The app uses the current DMK packages, not `@ledgerhq/hw-app-eth`:

```bash
npm install @ledgerhq/device-management-kit \
  @ledgerhq/device-signer-kit-ethereum \
  @ledgerhq/device-transport-kit-web-hid
```

The connector in `console/lib/wallet.ts` builds the DMK once with
`webHidTransportFactory`, discovers a device, connects a session, and uses
`SignerEthBuilder(...).build()` for:

- `getAddress("44'/60'/0'/0/0")`
- `signTypedData("44'/60'/0'/0/0", { domain, types, primaryType, message })`

The DMK actions are RxJS observables; the app resolves the first completed action
and cancels/subscribes correctly. WebHID is available in Chrome and Edge. Android
Chrome support depends on the device and USB-OTG; the dev signer remains the
phone fallback.

### Supported devices tested

**No physical Ledger device was available in this environment.** The direct
connector follows the current DMK Ethereum signer API but has not been exercised
against a physical Nano S Plus, Nano X, Flex, or Stax. The EIP-712 payload and
the contract recovery path are covered by the Hardhat signature suite. Treat the
Ledger path as requiring a device smoke test before the demo.

The browser-wallet path is also not exercised against a physical MetaMask
installation here; the typed-data builder and contract signature path are tested
independently.

## Pre-demo checklist

1. Close Ledger Live. It holds the WebHID device and the DMK connection will fail.
2. Unlock the Ledger.
3. Open the **Ethereum** app on the device. If it is closed, the DMK device
   action reports the app error.
4. Confirm the firmware and Ethereum app are current enough for EIP-712 signing.
5. Use Chrome or Edge with WebHID enabled.
6. Use the default derivation path `44'/60'/0'/0/0`, or record the path used by
   the account you funded.
7. Put the device on the same chain ID as the app (`31337` locally, `11155111`
   on Sepolia).
8. Fund the account with governance tokens. Voting weight is read from the
   governor's voting token at the time the vote is cast; an account with zero
   tokens reverts with `InsufficientVotingPower`.
9. For guardian halts, the connected account must equal `IntentLockExecutor.guardian()`.
   If it does not, the app disables the hardware halt and shows the guardian
   address.

## What the device displays

The exact rendering depends on the Ethereum app version and the available
clear-signing metadata. For the custom `IntentVote` and `IntentHalt` types:

- The device should show the domain (AegisIntentGovernor or
  AegisIntentLockExecutor), chain ID, and the typed-data fields when the app
  supports the type.
- If the app does not have clear-signing metadata for these custom types, it may
  show a **blind-signing warning and a typed-data hash** instead of the fields.
  Do not approve a blind-signing screen for a high-value action.
- The app's **Verify on your device** panel always shows the exact fields used to
  build the typed data: proposal, commitment, support, brief hash, statement,
  nonce and deadline. Compare them with the device before approving.

This is an honest limitation: the app cannot force a Ledger to render custom
EIP-712 fields as prose unless the device has a clear-signing descriptor for the
type. A blind-signing screen is a real possibility with a custom type.

## What the hardware wallet does NOT guarantee

- It does not prove that the statement is a fair reading of the proposal. The
  statement is generated by the app from the committed rules; a compromised app
  could show different prose.
- It does not protect against a compromised governor or executor. The
  commitment and the contract are the boundary.
- It does not make a bad approval safe. It binds the exact signed action; it does
  not judge whether the action is wise.
- It does not protect the guardian role if the device key is not the configured
  guardian. The contract checks `signer == guardian`.
- It does not prevent a relayer from withholding the transaction. The relayer
  can refuse to submit; it cannot change a signed field without invalidating the
  signature.
- It does not guarantee the device firmware, the app, or the host machine are
  uncompromised.

## Relayer and environment

The relayer pays gas and submits already-signed payloads. It never sees a voter
or guardian private key.

| Variable | Purpose |
| :--- | :--- |
| `RELAYER_KEY` | Funded relayer key for Sepolia; on local Hardhat a funded dev account is used |
| `GUARDIAN_KEY` | Server guardian key used only by the Auto halt mode |
| `GUARDIAN_ADDRESS` | Set the guardian to a hardware wallet on a Sepolia deployment |
| `NEXT_PUBLIC_CHAIN_ID` | App chain (31337 local, 11155111 Sepolia) |
| `NEXT_PUBLIC_RPC_URL` | Browser-wallet chain RPC (the phone cannot reach `127.0.0.1`) |

The local default guardian is Hardhat account index 1. The default relayer is
account index 9. `GUARDIAN_MODE=hardware npm run seed` leaves the P2 commitment
queued with a pending Sentinel report so the guardian flow can be signed;
`GUARDIAN_MODE=auto npm run seed` keeps the original automatic software halt.

To use a hardware wallet as the guardian on Sepolia:

```bash
# .env
GUARDIAN_ADDRESS=0xYourLedgerAddress
RELAYER_KEY=0xFundedRelayerKey
NEXT_PUBLIC_CHAIN_ID=11155111
```

Deploy and seed, then connect the Ledger with the matching account. The Auto
mode will not work for a hardware guardian unless `GUARDIAN_KEY` is also
available to the server; the Hardware-confirmed mode is the intended path.

## API and test commands

- `GET /api/live/signing-config?govId=…&voter=0x…&signer=0x…` returns the
  domains, nonces, statement, brief hash, deadline and pending halt.
- `POST /api/live/relay-vote` submits `voteBySig`.
- `POST /api/live/relay-halt` submits `haltBySig`.
- `POST /api/live/auto-halt` uses the guardian dev/software key.
- `GET /api/live/account-state?address=0x…` feeds the preflight.

Run the signature contracts and the typed-data builder:

```bash
npx hardhat test test/redteam/signature-flows.test.ts
npm run test:parity
cd console && npm test && npm run typecheck && npm run lint
```

The contract suite covers valid signatures, wrong signer, expiry, replay,
domain separation, tampered fields, double voting, guardian-only halts and the
post-halt execution refusal. The app tests cover the typed-data builder and
statement renderer.
